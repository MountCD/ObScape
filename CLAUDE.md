# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
cargo build                      # build workspace
cargo run -p ob_core             # run the HTTP server binary
cargo run -p ob_core -- --help   # CLI flags (--config, --database, --init, --verbose, --allow-autogenerated, --print-config)
cargo test                       # unit tests (ob_common) + handler/control tests (ob_core/src/server.rs, control.rs), no Postgres needed
cargo test -p ob_common <name>   # run a single test by name in one crate
OBSCAPE_TEST_DATABASE_URL=postgres://... cargo test -p ob_core   # also runs the end-to-end chat test (real Postgres, mocked upstream)
cargo fmt --all -- --check && cargo clippy --all-targets -- -D warnings   # what CI runs before build/test
cd python && python3 -m unittest discover -v   # stdlib-only client library (no pytest, no deps)
```

CI (`.github/workflows/rust.yml`) runs fmt-check, clippy with `-D warnings`, build and test on push/PR to `master`, plus a `python` job running `cd python && python3 -m unittest discover -v`. A throwaway `docker run --rm -e POSTGRES_PASSWORD=pw -p 15433:5432 postgres:16` is enough for the end-to-end test.

Runtime requires a reachable PostgreSQL instance (`database_url` in config). There is no migration tool — `Database::open_db` issues `CREATE TABLE IF NOT EXISTS` for `messages` and `chats` plus an index on every connect. `Database::connect_lazy` exists only so handler tests can build an `AppState` without a server.

Docker: `cp .env.example .env`, fill it in, then `docker compose build && docker compose up` brings up `postgres:16` (named volume `pgdata`, `pg_isready` healthcheck that `ob_core` waits on via `depends_on: condition: service_healthy`) plus the server; both services have `restart: unless-stopped`. `docker-compose.yml` bind-mounts `./config.toml` (gitignored, must exist first with `autogenerated = false`) read-only to `/home/obscape/config.toml` and sets `OBSISTENT_DATABASE` to `postgres://<POSTGRES_USER>:<POSTGRES_PASSWORD>@db:5432/<POSTGRES_DB>` — the env override beats whatever `database_url` the mounted config has. `POSTGRES_USER`/`POSTGRES_DB` default to `postgres`/`obscape`, `POSTGRES_PASSWORD` is required (`${VAR:?}`), and `OB_PORT` picks the host port (default 11080). `.env` is also passed to `ob_core` via `env_file` (`required: false`) so `OBSISTENT_AGENT_*_API_KEY` and `OBSISTENT_API_TOKEN` reach the server. `ob_core` also gets `extra_hosts: host.docker.internal:host-gateway` — with `api_url = "http://127.0.0.1:1234"` the container would talk to itself, so a model on the host must be addressed as `host.docker.internal` **and** must listen on `0.0.0.0` (a loopback-only bind refuses the bridge gateway too). The multi-stage `Dockerfile` uses `cargo-chef` for dependency caching, builds only `-p ob_core` with `--locked` in release mode, and copies the binary into `debian:trixie-slim` (+`ca-certificates`) running as the non-root `obscape` user with `OBSISTENT_CONFIG=/home/obscape`. The runtime stage creates `/home/obscape` via `install -d -o obscape -g obscape` — required: Docker creates the bind-mount's parent directory as root `0755`, and without the chown the process cannot create `control.sock` there (exit 6, `failed to bind control socket ... Permission denied`); the socket path is therefore `<config dir>/control.sock` in-container unless `control_socket` says otherwise, and reaching it from the host needs an extra writable mount. `.dockerignore` keeps `config.toml`, `.config/` and `.env` out of the build context.

## Architecture

Cargo workspace (edition 2024, resolver 3) with three crates layered bottom-up:

- **`ob_common`** — shared primitives, no knowledge of HTTP.
  - `config.rs`: `Config` / `AgentConfig`, TOML loading, hand-rolled argv parsing. `parse_cli()` is the single entry point that reads argv+env into an opaque `PathOverrides`; `main` parses once and threads it through `resolve_config_path` / `init_config` / `load_config`. `parse_args` itself takes argv and env values as parameters so it is unit-testable.
  - `database.rs`: `Database` (thin `PgPool` wrapper) and the wire types. `JsonMessageContent { role, content: ContentStruc }` is the DB row shape; `LlmMessage { role, content: String }` (built via `From<&JsonMessageContent>`) is what actually goes upstream inside `JsonRequestMessage`. `export_chat_recent(chat_id, limit)` returns system messages plus the last N others in chronological order — that is what the LLM sees; `export_chat` is the full dump. `create_chat` writes the `chats` row and the system prompt in one transaction; `add_message` returns the row id so `delete_message` can roll it back.
  - `agent.rs`: `make_request_with(http, cfg, agent, &[JsonMessageContent])` — the only place an upstream LLM is called. It dispatches on `AgentConfig.backend`: `Backend::OpenAI` (default) is OpenAI-compatible chat completions with bearer auth, `Backend::Ollama` goes through `ollama-rs` (`Ollama::try_new(api_url)`, model = `model_id`, no key; the reqwest timeout does not apply there, so `timeout_secs` is enforced with `tokio::time::timeout`). Both paths send the history **as is**: the caller must already have persisted the user message. Non-2xx upstream status → `AgentError::Other("upstream returned <status>")`, response body only in verbose log (`vlog!`); Ollama failures → `AgentError::Other("ollama: ...")`. `resolve_agent` looks up `config.agents[key]` and rejects `enabled = false`.
  - `time.rs`: dependency-free ISO-8601 UTC timestamps. Message `time` is stored as TEXT and ordered lexicographically in SQL, so keep the `YYYY-MM-DDTHH:MM:SS.mmmZ` format.
  - `verbose.rs`: `vlog!(&cfg, ...)` and `vdbg!(&cfg, expr)` macros — print to stderr with a `[verbose] file:line]` prefix only when `cfg.verbose`. `vdbg!` returns the value like `dbg!`. Use these instead of ad-hoc `if cfg.verbose`.
- **`ob_lib`** — `Assistant`, the orchestration layer. Errors funnel into `ObScapeError::{Db, Llm, BadRequest, Internal}` (implements `Display`/`Error`). The `reqwest::Client` is built here with a connect timeout and a default request timeout. The config lives in `cfg: RwLock<Arc<Config>>`: `config()` returns a snapshot (`Arc<Config>`) used for the whole request, `replace_config()` swaps it atomically for `set`/`reload` (it rejects a `database_url` change, `http_bind`/`control_socket` are rejected before it is even called). Never hold the lock across an await — take a snapshot and pass `&cfg` around, which is what every `vlog!`/`vdbg!` call site does.
  - `create_chat`: pick agent (explicit key, else `Config::main_agent()`) → `INSERT INTO chats ... RETURNING chat_id` → write the system prompt (`shared_prompt` + `personality_prompt`, joined by a blank line) as a `System` message once → delegate to `send_message`.
  - `send_message`: `chat_agent_for_user(chat_id, user_id)` — a chat owned by another user is indistinguishable from a nonexistent one (`BadRequest("unknown chat_id")`) → save user message → `request_reply` (`export_chat_recent(chat_id, cfg.history_limit)` → `make_request_with`) → save assistant reply. If `request_reply` fails, the user message is deleted again so a retry does not leave two consecutive `user` turns.
- **`ob_core`** — the binary. `main.rs` handles `--help`/`--init` first (so they never create files), auto-generates a config if missing, loads config (then `--print-config`), installs a `tracing_subscriber` (stderr; `info`, plus `tower_http=debug` when verbose; `RUST_LOG` overrides), opens the DB, warns if no `api_token` is set on a non-loopback bind, binds the control socket (before HTTP — a busy path must fail loudly, exit code 6) and spawns `control::serve`, then serves the Axum router with a SIGINT/SIGTERM graceful shutdown that also unlinks the socket. `server.rs` holds `AppState { assistant, db }`, DTOs, `validate_message` (empty / >16 KiB chars → 400), `require_token` middleware (only on `/v1/chat/*`, constant-time compare, 401; the token is read from `state.assistant.config()` on every request, not stored in `AppState`, so a `set` that changes `api_token` takes effect without restart), a DB-aware `health` (`SELECT 1` with 2 s timeout → 503 `degraded`), and `AppError` whose `status()` maps `Db`/`Internal` → 500, `Llm` → 502, `BadRequest` → 400; the message text comes from `Display`. The router is wrapped in `tower-http` layers: body limit 64 KiB (413), request timeout 180 s (408), `TraceLayer`.

New behaviour belongs in `Assistant` (`ob_lib`) so the DB/LLM sequencing is not duplicated; handlers in `ob_core/src/server.rs` should stay thin validation + DTO shims.

Note: `ob_core/src/server.rs` refers to `crate::Assistant`, `crate::config`, `crate::database`, `crate::ObScapeError` — these resolve through the `use` statements at the top of `main.rs`, not through a `lib.rs`. Adding an import there changes what `server.rs` can see.

## Endpoints

- `GET  /v1/health` — `{ status: "ok", db: "ok" }` or 503 `{ status: "degraded", db }`; never requires a token
- `POST /v1/chat/new` — `{ user_id, message, agent? }` → `{ chat_id, time, message, tools }`; `agent` omitted → the enabled agent with `main = true` (at most one is allowed, checked in `load_config`)
- `POST /v1/chat/message` — same response shape, takes `{ user_id, chat_id, message }`

`agent` is a key in `config.agents` (a `HashMap<String, AgentConfig>`), not a fixed enum — agents are defined entirely in TOML and are chosen only at chat creation. `time` in responses is Unix seconds; `tools` is always empty for now. Authentication is a single shared bearer token (`api_token` / `OBSISTENT_API_TOKEN`); when unset the chat routes are open. `user_id` is still trusted from the request body, so the ownership check only stops accidental cross-chat access, not a forged `user_id` by a token holder.

## Config

`--config` takes the **directory** holding `config.toml`, not the file path: `resolve_config_path` returns the directory and `format_conf_path` appends `/config.toml`. The default directory is `$HOME/.config/obscape` via `env::home_dir()` (`ConfigError::NoHomeDir` if unset).

Precedence: CLI > env > TOML. `main` loads `.env` from the working directory first (`dotenvy`, never overriding real env). The env vars read are `OBSISTENT_CONFIG` (config **directory**), `OBSISTENT_DATABASE` (database URL), `OBSISTENT_API_TOKEN` and `OBSISTENT_AGENT_<NAME>_API_KEY` per agent (`agent_api_key_env` normalizes the agent key: uppercase, non-alphanumerics → `_`). `api_key` in TOML is optional; `load_config` errors if an enabled agent ends up without a key. The `Dockerfile` sets `OBSISTENT_CONFIG=/home/obscape`. `config.toml`, `.config/` and `.env` are gitignored and dockerignored (config is bind-mounted at runtime, secrets come from `.env`; `.env.example` is the template).

Optional TOML fields with serde defaults: `autogenerated` (false), `verbose` (false), `history_limit` (50), `api_token` (none), `control_socket` (none → `<config dir>/control.sock`) on `Config`; `main` (false), `backend` (`"openai"`, serde `lowercase` — `"ollama"`), `api_key` (empty) and `timeout_secs` (120) on each agent. `validate_config` (unit-tested, no file I/O) applies the env overrides and rejects `history_limit = 0`, more than one `main` agent, enabled agents with an empty key/model — for `backend = "openai"` an `api_key` and a full http(s) `api_url` are required; for `backend = "ollama"` neither is (and `api_url` is a bare server address such as `http://127.0.0.1:11434`).

The template written by `--init` sets `autogenerated = true`; `load_config` refuses to start while that flag is set (returns `ConfigError::Autogenerated`, and outside containers also opens the file via `xdg-open`/`notepad`). `--allow-autogenerated` is the only bypass. `is_containerized()` (checks `OBSISTENT_NO_EDITOR`, `/.dockerenv`, `$container`, `/proc/1/cgroup`) gates every attempt to spawn an editor — keep new editor-spawning paths behind it.

`api_url` is POSTed to as-is, so for an OpenAI-compatible upstream the path is mandatory (`http://host.docker.internal:1234/v1/chat/completions`; a bare `http://host:1234` silently POSTs to `/` and many upstreams answer that with 200/405). `backend = "openai"` also requires a non-empty `api_key` even for local servers that ignore it (LM Studio, llama.cpp): keep a dummy in `config.toml` or set `OBSISTENT_AGENT_<NAME>_API_KEY`. The shared `reqwest::Client` (one per `Assistant`) sets only a connect timeout and a default request timeout; per-agent `timeout_secs` overrides the request one.

When a chat seems to hang (client aborts or gets 502 after exactly the agent timeout), suspect the upstream before the backend: `/v1/models` answering instantly proves nothing, a completion is orders of magnitude heavier. Running under Compose, the tie-breaker is a direct call to the host that bypasses the container:

```bash
curl -s -m 300 -w '\n[HTTP %{http_code} за %{time_total}s]\n' \
  -H 'Content-Type: application/json' -d '{"model":"<id>","messages":[{"role":"user","content":"hi"}],"max_tokens":8}' \
  http://192.168.100.8:1234/v1/chat/completions
```

`--print-config` and the verbose startup log print `database_url` through `mask_db_password` (`user:***@host`); keep any new output of the URL or agent `api_key` masked the same way. `Config::masked()` is the general form used by the control socket `get` — it clones the config and replaces the DB password, every enabled agent's `api_key` and `api_token` with `***` (`masked_toml()` serializes that). Never print an unmasked config through a new code path.

## Control socket (`ob_core/src/control.rs`)

A Unix-domain socket lets a running core re-read or accept a new config without a restart. Path: `control_socket` from TOML if set, otherwise `<config dir>/control.sock`; created with mode `0600`, unlinked on shutdown, and `bind()` removes a stale file left by a dead process (after failing to probe-connect it). Protocol — one JSON command per connection, one line each way:

```text
{"cmd":"ping"}                  -> {"ok":true,"service":"obscape"}
{"cmd":"get"}                   -> {"ok":true,"config":"<TOML, secrets masked>"}
{"cmd":"reload"}                -> {"ok":true}
{"cmd":"set","config":"<TOML>"} -> {"ok":true}
{"cmd":"anything-else"}         -> {"ok":false,"error":"..."}
```

Commands are ≤1 MiB, handled synchronously on the accept loop (`dispatch`/`run` are plain `fn`, `tokio::spawn(serve(...))` runs the loop). `reload` re-reads `config_path` through `config::reload_config` (same loader as startup, no editor spawn); `set` parses+validates the text first, then writes the file with rollback of the previous bytes on any later failure. Both reject configs that differ in `database_url`, `http_bind` or `control_socket` (`check_appliable` — those need a restart) and configs containing masked `***` values (`looks_masked` — a client echoing back `get` output must not wipe its secrets). Every successful change goes to `Assistant::replace_config`, which swaps the `RwLock<Arc<Config>>` — HTTP handlers pick it up on their next request. Tests cover each command, rollback, 0600 perms, stale-socket rebind and one full round trip over a real socket; they are `#[tokio::test]` because `Assistant::new` builds a sqlx pool.

## Python client library (`python/`)

`python/obscape/` is a dependency-free (stdlib only) package: `ObScapeClient` for the HTTP API (`health`, `new_chat`, `send_message`; `ApiError` carries `status`/`payload`, a 503 health reply is returned, not raised) and `ConfigControl` for the socket (`ping`, `get`, `get_dict`, `reload`, `set`, `set_from_file`; errors are `ControlError`). Packaged via `python/pyproject.toml` (`pip install ./python`), documented in `python/README.md` and in `docs/python/`, tested with plain `python3 -m unittest discover` in `python/` — `python/tests/` fakes both the socket and the HTTP server, no running core needed. Keep it dependency-free and in sync with the Rust protocol/tests.

## Documentation (`docs/python/`)

`docs/python/` is the reference documentation for the Python package: `README.md` (overview, quick start, public exports), `client.md` (`ObScapeClient` and its errors), `control.md` (`ConfigControl`, socket path resolution, errors, constants) and `protocol.md` (the HTTP and control-socket protocols that must stay in lockstep with the Rust side).

**After any change to `python/obscape/`, `python/pyproject.toml`, `python/README.md` or the protocols they mirror (endpoints in `ob_core/src/server.rs`, the control socket in `ob_core/src/control.rs`, `OBSISTENT_*` env handling), update the relevant files in `docs/python/` in the same commit.** In particular: a new/changed method or error → `client.md`/`control.md`; a changed wire format, status code or path resolution → `protocol.md`; a changed public export, install step or version bump → `README.md` and the version table in `protocol.md`. Keep the docs in the same style (Russian, tables for parameters/errors).

## Tool calling (work in progress)

Tool/MCP support is partly built and not wired into the request flow yet:

- `ob_common/src/tools/`: `Tool` trait + `ToolResponse`/`ToolErrors` (`tool.rs`), `Executor { name, args: serde_json::Value }` (`executor.rs`), and `ToolRegistry` (`registry.rs`), whose methods are still `todo!()`. `ob_common/src/mcp/` is a placeholder module.
- Config: `Config.mcp_file` (path to an `mcp.json` listing the available tools) and `AgentConfig.tools: HashMap<String, ToolRights>` (`Approve` / `Ask` / `Deny`, keyed by tool name for now). Neither has a serde default, so every `config.toml` and agent block must set them (`mcp_file = "..."`, `tools = {}`).
- Database: `Roles` has a `Tool` variant (`"tool"`); `messages` gained nullable `tool_calls` (JSON-serialized `Vec<ToolCall>`, assistant rows only) and `tool_call_id` (tool rows only). `From<&JsonMessageContent> for LlmMessage` sets these fields per role. `CREATE TABLE IF NOT EXISTS` will not add the columns to an existing table — an older DB has to be migrated or recreated by hand.
- `agent.rs` defines `LlmReply::{Text, ToolCalls}`, but `Assistant` still only handles plain text replies; the `tools` field in API responses is still always empty.

`REVIEW.md` is an external review of the codebase (no source changes came with it).

## Conventions

Doc comments and user-facing CLI/log strings are largely in Russian; match the surrounding file rather than translating. Verbose output goes through the `vlog!`/`vdbg!` macros (stderr), never bare `dbg!`/`println!`. `AGENTS.md` just points here.
