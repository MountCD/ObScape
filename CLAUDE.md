# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
cargo build                      # build workspace
cargo run -p ob_core             # run the HTTP server binary
cargo run -p ob_core -- --help   # CLI flags (--config, --database, --init, --verbose, --allow-autogenerated, --print-config)
cargo test                       # unit tests (ob_common) + handler tests (ob_core/src/server.rs), no Postgres needed
cargo test -p ob_common <name>   # run a single test by name in one crate
OBSCAPE_TEST_DATABASE_URL=postgres://... cargo test -p ob_core   # also runs the end-to-end chat test (real Postgres, mocked upstream)
cargo fmt --all -- --check && cargo clippy --all-targets -- -D warnings   # what CI runs before build/test
```

CI (`.github/workflows/rust.yml`) runs fmt-check, clippy with `-D warnings`, build and test on push/PR to `master`. A throwaway `docker run --rm -e POSTGRES_PASSWORD=pw -p 15433:5432 postgres:16` is enough for the end-to-end test.

Runtime requires a reachable PostgreSQL instance (`database_url` in config). There is no migration tool — `Database::open_db` issues `CREATE TABLE IF NOT EXISTS` for `messages` and `chats` plus an index on every connect. `Database::connect_lazy` exists only so handler tests can build an `AppState` without a server.

Docker: `docker compose build && docker compose up` brings up `postgres:16` plus the server; `docker-compose.yml` bind-mounts `./config.toml` (gitignored, must exist first) to `/etc/obscape/config.toml`. The multi-stage `Dockerfile` uses `cargo-chef` for dependency caching and builds only `-p ob_core`.

## Architecture

Cargo workspace (edition 2024, resolver 3) with three crates layered bottom-up:

- **`ob_common`** — shared primitives, no knowledge of HTTP.
  - `config.rs`: `Config` / `AgentConfig`, TOML loading, hand-rolled argv parsing. `parse_cli()` is the single entry point that reads argv+env into an opaque `PathOverrides`; `main` parses once and threads it through `resolve_config_path` / `init_config` / `load_config`. `parse_args` itself takes argv and env values as parameters so it is unit-testable.
  - `database.rs`: `Database` (thin `PgPool` wrapper) and the wire types. `JsonMessageContent { role, content: ContentStruc }` is the DB row shape; `LlmMessage { role, content: String }` (built via `From<&JsonMessageContent>`) is what actually goes upstream inside `JsonRequestMessage`. `export_chat_recent(chat_id, limit)` returns system messages plus the last N others in chronological order — that is what the LLM sees; `export_chat` is the full dump.
  - `agent.rs`: `make_request_with(http, cfg, agent, &[JsonMessageContent])` — the only place an upstream LLM is called (OpenAI-compatible chat completions, bearer auth, per-agent `timeout_secs`). It sends the history **as is**: the caller must already have persisted the user message. Non-2xx upstream status → `AgentError::Other("upstream returned <status>")`, body only in verbose log. `resolve_agent` looks up `config.agents[key]` and rejects `enabled = false`.
  - `time.rs`: dependency-free ISO-8601 UTC timestamps. Message `time` is stored as TEXT and ordered lexicographically in SQL, so keep the `YYYY-MM-DDTHH:MM:SS.mmmZ` format.
  - `verbose.rs`: `vlog!(&cfg, ...)` and `vdbg!(&cfg, expr)` macros — print to stderr with a `[verbose] file:line]` prefix only when `cfg.verbose`. `vdbg!` returns the value like `dbg!`. Use these instead of ad-hoc `if cfg.verbose`.
- **`ob_lib`** — `Assistant`, the orchestration layer. Errors funnel into `ObScapeError::{Db, Llm, BadRequest, Internal}` (implements `Display`/`Error`). The `reqwest::Client` is built here with a connect timeout and a default request timeout.
  - `create_chat`: pick agent (explicit key, else `Config::main_agent()`) → `INSERT INTO chats ... RETURNING chat_id` → write the system prompt (`shared_prompt` + `personality_prompt`, joined by a blank line) as a `System` message once → delegate to `send_message`.
  - `send_message`: `chat_agent_for_user(chat_id, user_id)` — a chat owned by another user is indistinguishable from a nonexistent one (`BadRequest("unknown chat_id")`) → save user message → `export_chat_recent(chat_id, cfg.history_limit)` → `make_request_with` → save assistant reply.
- **`ob_core`** — the binary. `main.rs` handles `--help`/`--init` first (so they never create files), auto-generates a config if missing, loads config, installs a `tracing_subscriber` when verbose, opens the DB, then serves the Axum router with a SIGINT/SIGTERM graceful shutdown. `server.rs` holds `AppState { assistant, cfg }`, DTOs, `validate_message` (empty / >16 KiB chars → 400), and `AppError` whose `status()` maps `Db`/`Internal` → 500, `Llm` → 502, `BadRequest` → 400; the message text comes from `Display`. The router is wrapped in `tower-http` layers: body limit 64 KiB (413), request timeout 180 s (408), `TraceLayer`.

New behaviour belongs in `Assistant` (`ob_lib`) so the DB/LLM sequencing is not duplicated; handlers in `ob_core/src/server.rs` should stay thin validation + DTO shims.

Note: `ob_core/src/server.rs` refers to `crate::Assistant`, `crate::config`, `crate::database`, `crate::ObScapeError` — these resolve through the `use` statements at the top of `main.rs`, not through a `lib.rs`. Adding an import there changes what `server.rs` can see.

## Endpoints

- `GET  /v1/health`
- `POST /v1/chat/new` — `{ user_id, message, agent? }` → `{ chat_id, time, message, tools }`; `agent` omitted → the enabled agent with `main = true` (at most one is allowed, checked in `load_config`)
- `POST /v1/chat/message` — same response shape, takes `{ user_id, chat_id, message }`

`agent` is a key in `config.agents` (a `HashMap<String, AgentConfig>`), not a fixed enum — agents are defined entirely in TOML and are chosen only at chat creation. `time` in responses is Unix seconds; `tools` is always empty for now. There is no authentication: `user_id` is trusted from the request body, so the ownership check only stops accidental cross-chat access, not a forged `user_id`.

## Config

`--config` takes the **directory** holding `config.toml`, not the file path: `resolve_config_path` returns the directory and `format_conf_path` appends `/config.toml`. The default directory is `$HOME/.config/obscape` via `env::home_dir()` (`ConfigError::NoHomeDir` if unset).

Precedence: CLI > env > TOML. The env vars actually read are `OBSISTENT_CONFIG` (config directory) and `OBSISTENT_DATABASE` (database URL) — note that `Dockerfile` sets `OBSISTENT_CONFIG_DIR` and `docker-compose.yml` sets `OBSISTENT_CONFIG_PATH`, neither of which the code reads, so containers currently fall back to the default path. `config.toml` and `.config/` are gitignored.

Optional TOML fields with serde defaults: `history_limit` (50) on `Config`; `main` (false) and `timeout_secs` (120) on each agent. Everything else is required.

The template written by `--init` sets `autogenerated = true`; `load_config` refuses to start while that flag is set (returns `ConfigError::Autogenerated`, and outside containers also opens the file via `xdg-open`/`notepad`). `--allow-autogenerated` is the only bypass. `is_containerized()` (checks `OBSISTENT_NO_EDITOR`, `/.dockerenv`, `$container`, `/proc/1/cgroup`) gates every attempt to spawn an editor — keep new editor-spawning paths behind it.

`--print-config` and the verbose startup log print `database_url` through `mask_db_password` (`user:***@host`); keep any new output of the URL or agent `api_key` masked the same way.

## Conventions

Doc comments and user-facing CLI/log strings are largely in Russian; match the surrounding file rather than translating. Verbose output goes through the `vlog!`/`vdbg!` macros (stderr), never bare `dbg!`/`println!`. `AGENTS.md` just points here.
